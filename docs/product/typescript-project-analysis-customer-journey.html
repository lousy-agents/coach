Customer Journey: TypeScript Project Analysis

This document starts with the customer outcome and judges solution choices by whether they make that outcome easier to reach. It guides discovery, product copy, and the eventual epic's acceptance criteria.

01 · Why this journey exists

The job the customer hires Coach to do

An agentic software engineer has a working TypeScript application. They want their coding agent to help improve its architecture, not merely produce more code.

They need to know whether Coach can usefully analyze this repository; what it found in their actual code and why it matters; what a focused refactor would look like, including residual uncertainty; and whether that refactor improved the architectural evidence.

“Can Coach help here?”
→
“It understands enough of my project to be credible.”
→
“My agent and I know exactly what to change.”
→
“The change made the evidence better.”
Coach succeeds when that loop is useful and repeatable. It is not enough for a command to start, for a dependency to install, or for a fixture to produce a prearranged finding.
Target customer and honest starting point Hypothesis

The candidate first persona is a project owner using a coding agent in their own TypeScript repository. This is a founder hypothesis, not a validated market segment. Interviews and pilot use must establish whether the person has this job, prefers this workflow, and will return after the first loop. It can inform this journey, its research prompts, and a narrow implementation epic; it cannot choose a durable persona, pricing, distribution model, or broader roadmap.

This candidate is comfortable using a terminal and a coding agent, but should not need to understand Coach’s JavaScript packaging, compiler APIs, process boundaries, or internal rule registries.

The journey starts with a working project, not a prepared Coach project. At that point, any of these may be missing:

  • Coach itself on PATH
  • a compatible Node and TypeScript environment
  • a committed Coach architecture policy
  • a supported tsconfig or framework pattern
  • a clear way to compare an agent’s uncommitted refactor with the prior scan
The journey must expose those gaps early and plainly. Hiding one behind an empty report, a mysterious dependency failure, or an analysis of different source than the agent just edited destroys trust.
02 · Commitments that outlive any implementation

Customer promises

These should hold regardless of how the implementation achieves them.

01

One understandable entry point

The customer starts from one obvious Coach entry point and understands the setup it needs without learning about internal analyzer components. Delivery packaging remains a solution hypothesis, not this invariant.

02

A fast, legible fit check

Before asking for setup or policy investment, Coach tells the customer whether it can analyze this project meaningfully: repository, code state, coverage, and gaps in language a human and agent can act on.

03

No surprise changes or invented success

Coach explains every project-changing action before it happens. It never silently installs a dependency, edits a manifest, uses the network during a scan, or presents a setup failure as a clean result.

04

Architectural intent belongs to the customer

Coach does not infer the architecture a team wants. A missing policy is a visible onboarding step, not a condition silently assumed by the first command.

05

The first result is useful, even without a defect

A coverage/fit summary or reachability fact can be a first win when it accurately explains what Coach saw. The product must not manufacture a finding to create a dopamine hit.

06

The agent can explain, change, and verify

Coach returns source-anchored, recommendation-grade evidence. The agent can propose a narrow change, assess behavioral protection, and explain what a rescan did and did not establish.

07

Limits are visible at the decision point

If a framework, import, source-to-sink path, or code state is outside covered analysis, Coach says so where the customer would otherwise act. “No matched finding” is not “the architecture is clean.”

03 · The ideal journey, moment by moment

Journey map

The journey begins when something outside Coach creates urgency. Coach belongs in the workflow only if it gives a clearer decision than inspecting a diff, running tests, tracing dependencies, or asking a reviewer to reconstruct intent.

Target journey Moments 0–10 define the intended experience. They do not describe a currently released TypeScript-project funnel. The current supportable path and its limits remain visible in the evidence boundary.
  1. 0
    Trigger

    “Why is the current review or refactor loop not enough?”

    Coach and agent experience

    The human and agent name the architectural or review uncertainty they are trying to reduce, and the current workaround that is falling short.

    Evidence of success

    The customer can say what a useful Coach result would let them decide.

  2. 1
    Discover

    “Can I use Coach on this TypeScript app?”

    Coach and agent experience

    The customer finds the Coach entry point without reading about internal analyzer components.

    Evidence of success

    coach is available; the documentation makes the next command obvious.

  3. 2
    Fit check

    “Will Coach understand enough of this repository to be useful?”

    Coach and agent experience

    Coach identifies the selected project and code state, then reports readiness: usable now, needs an explicit prerequisite, needs policy configuration, or outside current support.

    Evidence of success

    The customer knows the shortest honest next step before an analysis failure occurs.

  4. 3
    Establish architectural intent

    “What behavior do I want Coach to check?”

    Coach and agent experience

    The customer and agent draft or review a small policy describing project roots, layers, forbidden boundaries, and any required intermediary layer. Coach explains coverage and asks for review rather than guessing.

    Evidence of success

    The customer can point to the boundary Coach will evaluate and understands how to change it intentionally.

    Open question: how does a TypeScript customer create the first policy?
  5. 4
    Prepare with consent

    “What must change before the scan can run?”

    Coach and agent experience

    If a prerequisite is missing, Coach names it, explains why, and offers only actions it can actually perform. A human or interactive agent explicitly approves any project or environment change.

    Evidence of success

    Setup either succeeds and returns to the scan, or stops clearly with no misleading report.

    Open question: is compatibility friction acceptable to this audience?
  6. 5
    See the project

    “What did Coach actually analyze?”

    Coach and agent experience

    Coach reports the requested revision/code state, relevant project roots, coverage, and recognized patterns before or alongside findings.

    Evidence of success

    The customer can tell whether the report applies to the app and change they care about.

    Open question: what does useful coverage look like?
  7. 6
    Meaningful insight

    “What should we improve?”

    Coach and agent experience

    Coach presents a concrete layer violation, a high-confidence bypass, or an informative reachability fact—with locations, explanation, and coverage context. If none exists, it says what was checked and offers the next useful action.

    Evidence of success

    The customer or agent can restate the evidence without inventing semantics.

  8. 7
    Refactor together

    “What is the smallest architecture-preserving change?”

    Coach and agent experience

    The agent inspects the evidence, local conventions, and relevant behavioral tests; it proposes a focused change and identifies when behavioral coverage should be added or remains uncertain.

    Evidence of success

    The human remains in control and understands the intended architectural effect, behavior evidence, and residual risk.

    Full agent-assisted refactor loop
    1. Ask Coach to assess fit or run the configured scan.
    2. Summarize the strongest applicable evidence in plain language, including coverage limits.
    3. Inspect the referenced code, the customer’s policy, and the tests or other evidence representing affected behavior.
    4. Propose the smallest change that addresses the evidence without weakening the intended architecture. When behavior is not credibly protected, add or recommend a behavioral test before treating a passing run as preservation evidence.
    5. Obtain human approval where the agent’s operating policy requires it.
    6. Apply the change and run the repository’s normal tests.
    7. Ask Coach to evaluate the same scope against the changed source.
    8. Explain separately what improved in architecture evidence, what supports behavioral preservation, and remaining uncertainty.
  9. 8
    Verify improvement

    “Did the change improve the intended evidence?”

    Coach and agent experience

    Coach analyzes the same requested scope against the changed code state and makes before/after evidence legible: resolved, remaining, newly introduced, or indeterminate.

    Evidence of success

    The customer sees a credible architecture improvement or an honest limitation—never an incomplete comparison treated as verified.

    Open questions: which code state, and can the comparison be trusted?
  10. 9
    Hand off

    “What can a reviewer trust about this change?”

    Coach and agent experience

    The human and agent carry architectural intent, code-state provenance, behavior evidence, Coach evidence, coverage limits, and residual uncertainty into the change’s review context.

    Evidence of success

    A reviewer can evaluate the change without reconstructing the agent’s reasoning from scratch.

    What travels into the review
    • The intent and approved architecture policy that motivated the change
    • The selected source state and comparison scope
    • The relevant behavior tests, or the stated absence of behavioral evidence
    • Coach’s source-anchored finding or fact and its before/after state
    • Coverage limits and residual uncertainty

    This is a desired experience boundary, not a promise that the current CLI publishes a review artifact or that a reviewer receives an automated Coach verdict.

  11. 10
    Repeat

    “Can we use this on the next agent change?”

    Coach and agent experience

    The team repeats the same small loop without re-learning setup or internal terminology.

    Evidence of success

    Coach becomes a voluntary part of the agent-assisted engineering workflow.

04 · Service blueprint, not a single funnel

Actor ownership and durable handoffs

These handoffs must be explicit in the product and in research sessions.

  1. Human ownerapproved goal, scope, policy, and consent
  2. Coachreproducible report with provenance and limits
  3. Coding agentproposed change and behavior evidence
  4. Review systemreview context naming evidence and uncertainty

Human project owner

Owns

The goal, selected code state, policy approval, setup consent, and refactor approval.

Needs to understand

What Coach can and cannot establish; what the agent proposes to change.

Durable handoff

Reviewed policy, explicit approvals, and the final review context.

Coding agent

Owns

Exploring code, drafting a policy or refactor, identifying relevant behavior tests, and explaining limits.

Needs to understand

The chosen scope, approved policy, source state, and Coach evidence.

Durable handoff

Proposed change, test/behavior evidence, and a before/after explanation.

Coach

Owns

Declaring fit, analyzed scope, findings/facts, diagnostics, and coverage limits—without mutating the project.

Needs to understand

Nothing implicit: the configured policy and requested source state.

Durable handoff

Reproducible report with provenance, evidence, and diagnostics.

Repository and review system

Owns

Persisting source, policy, commits, tests, and the reviewable change.

Needs to understand

Which report and test evidence correspond to the reviewed revision.

Durable handoff

Committed source/policy and a review artifact that names evidence and uncertainty.

05 · How this plays out

High-value scenarios

All four are legitimate first interactions. Only one involves a defect.

A supported project, a meaningful finding

Finding path

The customer finds Coach, asks for a fit check, confirms a small architecture policy, and runs a scan. Coach recognizes the relevant configuration and reports an import that crosses a forbidden boundary. The agent explains the dependency, proposes a policy-preserving change, checks relevant behavior is protected or recommends a missing behavioral test, and asks Coach to compare changed code with the earlier scan.

The first win is not “TypeScript was installed.” It is “Coach gave my agent a specific, credible reason to change this dependency, and we could verify the result.”

A project that is not ready yet

Recovery path

The customer asks for a fit check but lacks a compatible environment, policy, or supported project shape. Coach says which one, what it checked, and what the customer can do next. It never emits a report that could be mistaken for a clean result.

This is a successful first interaction when it saves the customer from debugging hidden setup or trusting a report that did not apply.

A supported, complete scan with no finding

No-finding path

Coach fully analyzes the selected source and policy, but no configured boundary or supported source-to-sink pattern produces a finding.

The safe decision is only that no configured, covered rule matched this revision—not that the architecture is compliant or behavior is safe.

Next action Record the baseline, review whether the policy covers the boundary the customer cares about, or inspect a higher-risk flow with the stated coverage in mind.

A supported scan with incomplete or uncertain coverage

Coverage-limit path

Coach recognizes the project but cannot fully resolve a configured import, route, source-to-sink path, or source scope.

The safe decision is that Coach cannot establish a complete architecture result for this revision.

Next action Inspect the diagnostic with the agent, correct configuration or project shape where possible, and carry the limitation into review rather than treating an absent finding as a pass.

06 · Left intentionally visible

Product questions the journey exposes

A technical design may answer these, but it must not make them disappear from the customer experience.

Which code state is Coach verifying?

Today coach codesignal analyzes immutable Git revisions. That protects reproducibility, but an agent’s uncommitted change is not part of a baseline rescan. The current product therefore requires a commit before Coach can verify a refactor, and must say so explicitly. The ideal journey may support an explicitly selected worktree snapshot or another clear comparison mode. Until then, documentation and output must show the analyzed revision and warn when uncommitted changes would make the result surprising.

Can Coach make a trustworthy change-comparison claim?

The agent needs more than a baseline report to claim that a refactor improved a change. When an added, renamed, copied, or otherwise unanalyzable path prevents a complete comparison, human-readable and structured output must identify the affected path and make lifecycle/counter conclusions indeterminate. A summary that says no change was introduced while relevant source was skipped is not an honest verification result.

How does a TypeScript customer create the first policy?

Layer violations and bypasses require a customer-owned policy. The existing project-config suggestion path is Go-only, so a TypeScript customer cannot yet experience “Coach helped me create a starting policy” as a first-run flow. The eventual epic must either begin after a reviewed, committed policy exists or provide a supported way to create one. The latter is not automatically in scope; the former is a real onboarding cost that must be documented.

Is compatibility friction acceptable to the first audience?

The proposed exact TypeScript pin and interactive-only install path may be a sound narrow-pilot choice. They are not universal customer requirements. The pilot should measure whether customers can complete setup in their actual agent environment, including after dependency updates and without a TTY.

What does useful coverage look like before a defect appears?

The customer needs a legible answer about framework, routing pattern, data-access pattern, aliases, source scope, and unsupported boundaries. A report must distinguish code included by project configuration from code that meaningfully represents the customer’s production concern, especially when a test file can be included in the same scan. A no-violation report should still say whether Coach saw the relevant parts of the application and what the next useful check is.

08 · How we would know

Pilot measures

Funnel measures

  • Time from first invocation to a legible fit result
  • Time from fit result to first meaningful evidence
  • Abandonment by missing Coach, environment, policy, unsupported project shape, or non-interactive setup
  • Percentage of customers who can identify the analyzed code state correctly
  • Percentage of findings that lead to an agent proposal and a reviewed change
  • Percentage of those changes with a credible rescan result
  • Voluntary repeat scans

Qualitative signals

Think-aloud sessions, agent transcripts, and post-task interviews should establish:

  • Can the customer explain selected source state, what Coach checked, and the most important coverage limit?
  • Do they feel in control of policy, installation, and refactor approval rather than delegated around by the agent?
  • Can they explain to a reviewer why the change was made, what behavior was checked, and what remains uncertain?
  • After credible verification, do they report relief, increased confidence, or another concrete moment of value—and name the evidence that produced it?
09 · Reality check

Current evidence boundary

This is a desired journey, not a statement that the whole path ships today. Release language must retain these distinctions.

Current, supportable observations

  • Documented product path A local Go baseline with configured layer policy is narrow and is not this complete TypeScript customer journey.
  • Documented constraint The CLI analyzes immutable Git revisions; a TypeScript project config must be committed at the analyzed revision.
  • Pilot evaluation The evaluation updated 2026-08-16 records re-verified foreign-repository TypeScript deployment and diff-mode blockers. It is a dated observation, not acceptance-backed proof of current behavior.

Target journey, not shipped

  • Raw TypeScript structural analysis is not a deployable foreign-repository TypeScript project experience. The target fit check, policy onboarding, safe setup, and agent loop remain planned.
  • TypeScript CLI layer-bypass and reachability facts are planned wiring, not current CLI capability.
  • Analysis of a dirty worktree is not supported; only committed revisions are analyzed.
  • Full source/rule/coverage/comparison/version provenance across text and structured reports, sufficient for a human and agent to make the same claim, holds unevenly today.
10 · Where the line is drawn

Delivery assumptions and guardrails

Hypothesis Delivery assumptions

  • Coach may ship its small analyzer as part of Coach itself, rather than asking customers to vendor a js/semantics/ tree or download another component.
  • Node and the exact supported TypeScript compiler are resolved from the customer’s project or a supported environment manager; preflight verifies compatibility before scanning.
  • Any installation or manifest change requires an explicit interactive choice; non-interactive runs fail clearly rather than installing silently.
  • The scan is offline and keeps requested project source separate from host-provided compiler code, so a dirty worktree cannot silently alter a report for a committed revision.
  • The first CLI outcomes under consideration are layer violations, TypeScript layer-bypass findings, and facts about possible route-to-sink reachability.

Record these implementation hypotheses in a versioned epic only when they create the customer outcomes above; change them if they fail those promises.

Boundary Scope

  • This document does not authorize implementation changes, issue creation, or a broader TypeScript roadmap.
  • It does not promise automatic code edits, a clean architecture verdict, universal framework support, or a new active defect signal for reachability.

Its purpose is to make customer friction visible before a solution becomes too locked in to question.
