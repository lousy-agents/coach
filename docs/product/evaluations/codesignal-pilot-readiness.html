Functional evaluation · coach codesignal

Can CodeSignal leave pilot?

A hands-on product assessment of the shipped CLI — run against this repository, five other local repos, and a set of purpose-built repros — answering one question for the product owner. Every gap is now linked to the issue that tracks it.

16 Aug 2026 HEAD 19b6628 ~50 CLI runs 6 repositories 2 verification passes 25 tracked issues

Verdict

Stay in pilot.

Not because the analysis is bad. The parser is fast, deterministic, and safe on foreign code, and several rules are genuinely good. The blocker is narrower and worse: diff mode — the capability that makes this a PR check — returns a confident all-clear on the two most common shapes of AI-assisted change. A brand-new file's findings are counted as zero introduced. A renamed-and-rewritten file is not analyzed at all. Everything downstream of diff mode — CI gating, a PR bot, a team rollout — inherits that false green.

The engine is further along than the product wrapper around it. Closing the two lifecycle gaps, the exit-code contract, and report ergonomics is weeks of work, not quarters — and it moves this to “expand to Go teams as an advisory PR check.”

Tracked in epic #282 — close the pilot-exit gaps

Method

What was verified, and how

This report has been through two passes. The first was a functional evaluation against a locally built binary. The second put a six-specialist team on the findings with one instruction: re-verify every single-observation claim before anyone writes it into an issue. Each gap below carries the result — re-verified means independently reproduced on a fresh repro, agent-run means observed but not re-run, and corrected marks a first-pass claim that did not survive.

That second pass earned its keep twice over: it killed four claims, deepened two others into sharper defects than first reported, and surfaced a silent failure worse than anything in the original evaluation. Every gap is now tracked as a GitHub issue, linked inline.

Corrected since first publication

The released binary does not report dev. v0.3.0 prints 0.3.0; GoReleaser's default ldflags apply and only local builds say dev. The real defect is that the report carries no tool version — narrower than first stated.

architecture.layer_bypass was never firing. It has no CLI wiring at all, so the stale-inventory delta is one rule, not two.

Write-side TOCTOU races are not missed in both languages. TypeScript covers them; the gap is Go-specific — and sharper than reported, since Go's act-call set contains no write, create, rename, or metadata call whatsoever.

Report ordering is not rule-then-path. It is lifecycle → severity → confidence → path. The real defect is that magnitude never participates in the sort at all.

Two evidence gaps were also largely refuted rather than confirmed — TypeScript path aliases, project references, and .tsx all work once the sidecar is vendored, and multi-root config suggestion works for Go. What remains is that none of it is regression-locked outside this repository.

Blockers · ranked

Gaps that keep this in pilot

G0

A dotless module path silences all project analysis

re-verified

Found during the second pass, after this report was first published — and it outranks everything below it. Two repositories, byte-identical apart from the go.mod module path, each declaring two layers and containing a real forbidden import:

$ coach codesignal --baseline --project-config coach-project.json --format json module layersrepro (dotless) layer findings: 0 coverage complete: True diagnostics: 0 exit: 0 module example.com/app (dotted) layer findings: 1 coverage complete: True diagnostics: 0

The forbidden edge is not merely unreported — searching the entire JSON report from the dotless run for the string transport returns nothing. The edge never entered the model.

pkg/projectmodel/go_imports.go:366 applies isStdlibImport before matching the import against any known module path, and that heuristic is “the first path segment has no dot.” So in a dotless-module repository every internal import classifies as stdlib. The code comment states the assumption that fails: “holds for every module path convention in use (domains always contain a dot).”

Three things make this the most severe silent failure found. It defeats every disclosure mechanism, including the qualified-verdict fix — coverage reports complete and no diagnostic is emitted, so nothing downstream has anything to report. It silences the product's best output, since configured layer violations are the highest-precision finding CodeSignal produces. And go mod init myapp produces exactly this — a dotless path is the default for any non-domain name.

Tracked in #284 — dotless-module stdlib misclassification
G1

A new file's findings are counted as zero introduced

re-verified

One commit adds one valid Go file carrying cognitive complexity 28, nesting depth 8, and a map mutation. The tool finds all three — then classifies them unknown and reports introduced_signals: 0.

$ git diff --name-status HEAD~1 HEAD A brandnew.go $ coach codesignal --base HEAD~1 --format json "summary": { "files_analyzed": 1, "active_signals": 3, "introduced_signals": 0, "existing_signals": 0, "resolved_signals": 0 } unknown complexity.cognitive_complexity brandnew.go cognitive_complexity=28 unknown complexity.max_nesting_depth brandnew.go max_nesting_depth=8 unknown state.hidden_input_mutation brandnew.go m["x"]

The README defines introduced as “present at HEAD, not present at the merge-base” and unknown as “the merge-base side could not be analyzed (e.g. it had a syntax error).” An added file is definitionally introduced. The shipped behavior contradicts the shipped contract. Note also that the counters do not sum: three active signals, and all four lifecycle buckets read zero.

The agent's composite case is worse. A commit that adds a risky new file and deletes a risky old one reports introduced: 0, resolved: 3 — a strictly worse change reading as a pure win. Any CI gate written the obvious way, fail if introduced_signals > 0, passes it.

Who it hurts: every consumer of diff mode — the entire PR-check story — and worst for the customer the PRD names, someone reviewing agent-generated code where new files dominate. Cost to close: small. The classifier cannot currently distinguish “no base version because the file is new” from “no base version because the base was unanalyzable”; they collapse to one value. The second pass confirmed the counters are broken twice, not once: unknown falls out of all four buckets and resolved is double-counted into active_signals.

Tracked in #262 — added-file lifecycle & summary counters
G2

Renamed files are skipped, and the headline says “no findings”

re-verified

A commit that renames a file and appends a 6-deep nested function with a map mutation. Git reports it as a 91%-similar rename; the tool analyzes nothing and exits 0.

$ git diff --name-status -M HEAD~1 HEAD R091 renamed.go moved.go $ coach codesignal --base HEAD~1 scope: production, filtered: 0, files analyzed: 0, active signals: 0, diagnostics: 1 No active CodeSignal findings. Diagnostics: path: moved.go, kind: unsupported_change_type, message: change status "R091" (rename/copy) is not supported exit=0

The limitation is documented — but the headline is a false all-clear, not “1 file could not be analyzed.” Agents rename and relocate constantly; a “reorganize the package” PR reports nothing at all. The behavior is also invisible from the outside: whether a change is analyzed depends on git's similarity heuristic, so the same logical edit is caught below the threshold and silently dropped above it.

The second pass found this is self-inflicted, and not really about renames at all. internal/codesignalcli/git.go:120 passes --find-copies-harder, which lets git treat an unmodified file as a copy source. Measured over this repository's last 200 non-merge commits:

coach's flags : A=520 M=588 C=8 D=6 git's default : A=528 M=588 C=0 D=6

All eight copy records are files git would plainly call A. The tool manufactures copy records out of ordinary new files and then drops them. The clearest example is a commit in this repository: fbfa1a0 dropped a 98-line new production .ts file as C058, reporting introduced: 0, resolved: 2, exit 0.

Cost to close: analyzing the head side of an R/C change as new content — even leaving lifecycle as unknown — is far cheaper than real rename tracking and removes the false all-clear. Reconsidering --find-copies-harder is cheaper still. Sequencing: #262 must merge first, or the natural fix here routes renamed files straight into that bug.

Tracked in #264 — renamed/copied files dropped silently #267 — the false all-clear verdict
G3

--project-config failures invert the documented exit contract

re-verified

The README states: “2 — a usage error… Usage guidance goes to stderr; nothing is written to stdout.” The observed behavior is exactly backwards.

$ coach codesignal --baseline --format json --project-config missing.json exit=2 stdout_bytes=243039 stderr_bytes=0 $ coach codesignal --baseline --format json --project-config /etc/passwd exit=2 stdout_bytes=242920 stderr_bytes=0

Under set -e the job dies with no message at all. Without it, a consumer happily ingests a 240 KB report that silently omitted the analysis it asked for. In text mode the only warning sits on line 2137 of a 2148-line report — and leaks a raw git error and exit code.

Compounding it, the documented suggest-then-use flow cannot work as written. --output writes to the worktree; --project-config reads at the git revision. The generated file is unusable until committed, and nothing says so — so the first thing a new user does fails, quietly. When it does work, the suggested candidate is 54 bytes with no layers or forbidden_imports, which is where all the value lives.

The second pass established this is not an oversight but a contradiction between two deliberate decisions. README.md:170 says exit 2 writes nothing to stdout; cmd/coach/project_contract_acceptance_test.go:25-26 locks in exit 2 with a full report on stdout and an empty stderr, and #208's failure-taxonomy table specifies that as intended. Meanwhile #48 Story 2 sets the opposite precedent for the analogous .coach.yaml case — two conventions for one situation.

Now ruled. CLI failures sort into three classes: usage errors, configuration errors, and partial-analysis conditions. Configuration errors are usage errors — exit 2, stderr, no stdout. A report that silently omits the analysis the user asked for is the same false green as G0 and G2, one layer up, and the degradation is undetectable because a failed schema-2 run emits a report byte-shape-indistinguishable from a legitimate schema-1 one.

Cost to close: small for the exit contract, now that the ruling exists. The round-trip separately needs the suggestion to emit something worth committing, or the step does not earn itself.

Tracked in #275 — config-failure exit contract #278 — suggest-project-config boundary #208 — taxonomy amendment
G4

TypeScript is second-class in two ways a TS team hits immediately

agent-run

--scope production does not exclude TypeScript tests. On a clean TS repo with src/app.ts and an identical src/app.test.ts, both scopes return byte-identical results. The exclusion is Go-only — coverage reports excluded: [{reason: test_only, language: go}] and nothing else. On a TS-only repo the flag is a no-op; on lousy-api-eval the only production-scope finding is an e2e test file.

TS project analysis cannot be deployed outside this repo. Following the README's own TypeScript example in a fresh repo produces a missing-sidecar diagnostic; hand-vendoring the sidecar yields a raw Node ERR_MODULE_NOT_FOUND stack trace inside the report; vendoring typescript too reaches an unresolvable platform package. To use the feature, a customer must reproduce this project's own js/semantics npm layout inside their repository.

Every one of those failures exits 0 with No active CodeSignal findings. For an architecture check, “the backend didn't run” and “your architecture is clean” must not be the same output.

The second pass quantified the customer payload: 586 files / 30 MB vendored at <repo>/js/semantics/, plus node on PATH — and it is platform-locked, since TypeScript 7 ships 20 mutually-exclusive platform packages. A working laptop run does not predict a working Linux CI run. It also refuted the tempting fix: a WASM backend would not dissolve this, because pkg/semantics' WASM build runs Go analysis inside JS — the opposite direction — while the sidecar depends on typescript/unstable/sync for module resolution.

Cost to close: the exit-0 false all-clear is small. Making the sidecar resolvable from the coach install — shipping it in the release archive, publishing to npm, or a --ts-sidecar-path flag — is real but bounded.

G5

The report can't be ranked, capped, or suppressed — so nobody will own it

agent-run

Baseline on this repo: 237 findings across 264 files, 2160 lines of text. 178 medium and 59 low; nothing high or critical. There is no “read this first,” no ignore or allowlist mechanism anywhere, and no published threshold rationale — a skeptical staff engineer asking “why is 25 a problem and 24 not?” has nowhere to look.

corrected The first pass said ordering is by rule then path. It is not — pkg/codesignal/sort.go:96-124 sorts by lifecycle group → severity → confidence → path, with rule id only sixth. The symptom was real, the diagnosis wrong, and the true defect is sharper: magnitude never participates in the sort at all. The first nine findings read 18, 15, 28, 19, 25, 17, 15, 116, 33. The second pass also found a fourth severity value, advisory, carried by architecture.layer_violation — which sorts below every low, so the one opt-in high-precision rule in the product lands last.

The noise is measurable on real code:

  • learn-go-with-tests — 60 of 79 findings (75%) are inside vendor/. Production scope does not exclude vendored code.
  • lousy-iam — 42 of 50 findings (84%) are one rule, state.hidden_input_mutation, 22 of them in a single file. Every one is violations.push into an explicitly named out-parameter on a void function. Technically true; the attached advice — “return a copy instead” — would be wrong here.
  • One 5-constructor file produced 10 findings: five identical density signals, twice, each with an empty evidence field. Two facts about one file, printed ten times, with no number attached. corrected — they are only identical in text; the JSON carries distinct subject, location, and fingerprint per signal, and the text renderer never prints subject. The underlying reading held: a file-level metric is emitted once per matching site.
  • 59 of 237 findings (25%) carry an empty evidence field — every pointer_return_density and constructor_density hit. Those findings are not adjudicable by a human, which also blocks the precision census below.

The PRD's own trust principle is “fewer, better findings,” and its success signal is voluntary repeat use. This report is neither, and no team runs it twice in this form.

Suppression — the one part of this already covered, by the .coach.yaml work under #48 — closes one of five sub-problems. The lousy-iam case is the sharpest reason why: push genuinely mutates, so the match is correct and the judgment is wrong. Suppression can only silence the whole file. That is a rule-precision problem, and the author had already written the discriminator into the types — readonly used 16 times in that file, the violations out-parameter deliberately not.

G6

Text output drops the two fields a human needs; diff mode has no provenance

agent-run

Text mode never prints rule_id or severity for file-local signals — you get an evidence string and infer the rule. The JSON for the same signal carries rule id, version, category, severity, confidence, fingerprint, and byte location; all of it is dropped on the way to the terminal. Layer-violation findings do print rule_id, so the formatter is inconsistent with itself. Meanwhile source_scope: unknown prints on 100% of findings in every default run — a dead field on every line of a user's first report.

Diff mode prints no provenance at all — no HEAD sha, no resolved merge-base — while baseline mode does. Since --base resolves through merge-base, pointing at a docs-only commit's parent silently pulled in 20 unrelated files and 17 signals with nothing in the output explaining what was compared. The merge-base surprise reproduced exactly on re-verification: --base 21efd94^ reported filtered: 20, files analyzed: 20, active signals: 17 against a merge-base of 6b7936b, with 73 files actually compared and none of that visible.

corrected The first pass reported that coach --version returns dev. That is true only of local builds — the published v0.3.0 binary prints 0.3.0, because GoReleaser's default ldflags apply. There is no release-identity defect, and adding ldflags would be a no-op. The real, unaffected defect is narrower: the report carries no tool version, so the PRD's stated goal of findings reproducible from recorded analyzer and rule versions is still not achievable.

Root cause

One table explains the blocker

Diff mode's correctness is entirely a function of how git labels the change. Two of the four labels are mishandled, and both mishandle toward silence. (G0 is a separate mechanism — it removes the import edge before any of this runs, and it affects baseline mode too.)

Git statusAnalyzed?Lifecycle assignedCounted asShould be
M — modifiedyesintroduced / existingcorrectly✓ correct
D — deletedyesresolvedresolved✓ correct
A — addedyesunknownnothingintroduced
R / C — renamedno—nothingintroduced / existing

The two rows that fail are the two that dominate agent-authored diffs. And the R/C row is largely self-inflicted: --find-copies-harder converts ordinary additions into copy records that are then discarded.

Working

What the pilot has already earned

  • Determinism and speed. Three identical runs hash identically. Baseline over 685 tracked files in 0.97s production / 1.43s all-scope. Clean exit-0 runs on five foreign repos including a 304-file one in 0.54s. No crashes, no hangs.
  • Fingerprint stability is the hard part, and it's right. Inserting a comment above flagged code kept every fingerprint stable and produced 6 findings, all correctly existing, zero false introduced. That is a real foundation for “new since last run.”
  • --build-target is the best idea in the product. It cut 264 files / 237 signals down to 111 / 128, correctly excluding code unreachable from that binary. “This code actually ships in the artifact” is defensible in a way “this file has branch_sum=68” is not.
  • Configured layer violations are the highest-quality output. Exact edge, exact line, machine-readable evidence, and a policy the user declared themselves — no threshold argument to have.
  • The TOCTOU recommendation is what actionable looks like — CWE-367, concrete Go API names, errors.Is(err, fs.ErrNotExist), a pointer to os.Root.
  • Usage errors are clean and leak nothing. Bad ref, non-git directory, bad format/scope/language, conflicting flags, empty diff, oversized file — all correct exit codes, stderr-only, no internals. Installation is credible: signed releases with checksums and a cosign bundle.

Survivable

Ship with a caveat rather than fix first

  • Security-rule recall is ~33%, and that's fine as long as you never market it. Six semantically identical TOCTOU patterns; two matched. Missed: the idiomatic Go guard-clause form, the os.IsNotExist form, and the TypeScript negated-guard form. corrected — the first pass said both write-side races are missed in both languages; TypeScript in fact covers them. The gap is Go-specific and sharper than reported: Go's act-call name set contains no write, create, rename, or metadata-mutation call at all, so the higher-severity write-side race is missed even in the fully supported gate shape. That is an act-name omission, far cheaper to fix than a dataflow limitation. The PRD is explicit this isn't a completeness guarantee, so no promise is broken — but it is the concrete reason the word “security” shouldn't leave the pilot yet. #205
  • JSON key presence is unstable. signals, diagnostics, coverage, subject, and evidence are omitted rather than emitted empty — five KeyErrors while writing throwaway consumers. Friction on the “consumable by CI” claim. Re-verification found five distinct top-level key sets and four per-signal sets from one binary, with 46% of signals lacking subject. Related: schema_version is 1 or 2 depending on a flag, not the tool version — and a failed schema-2 run degrades silently back to 1. #269
  • A dirty working tree is silently ignored. Staged and untracked files are invisible with no warning. Correct by design — analysis reads committed bytes — but it forecloses the pre-commit use case and will confuse people. A one-line “analyzing revision <sha>; N uncommitted changes” notice closes the confusion; the capability itself is a separate ask. #265 #168
  • --build-target needs a Go toolchain on PATH in the analyzed environment, which quietly undoes the self-contained-binary story. Good error message; document the constraint next to the flag. It also fires in repositories containing zero Go files, and is a silent no-op under --scope all — which turned out to be a design question in its own right, resolved below. #63 #283
  • Positional args are worse than swallowed. Go's flag stops at the first non-flag token, so every flag after one is silently discarded: --baseline foo bar --format json returns text, exit 0, empty stderr. You ask for JSON and get text. #273
  • The PRD's rule inventory is stale — it omits architecture.layer_violation, which the CLI emits today. corrected — the first pass also named architecture.layer_bypass, but that rule has no CLI wiring and was never firing. The delta is one rule, not two. #274

Limits

Evidence that could not be obtained

These bound the verdict and should be read as unresolved, not as absent problems.

  • TypeScript project analysis on any repo but this one. It was proved to fail elsewhere; it was proved to work only inside a clone of this repo with its own node_modules. largely refuted — the second pass vendored the sidecar and exercised all three named scenarios successfully: tsconfig paths aliases, solution-style project references (3 projects analyzed), and .tsx. Workspace package-name imports resolve even without a paths entry. What remains is that none of it is regression-locked, and no test runs the real sidecar from any repository but this one. #218
  • Multi-module / monorepo config suggestion. refuted — multi-root output works. Three go.mod files produced three roots; a go.work workspace produced three more. The single-root observation was an artifact of only testing single-module repos. The real gap is different and was missed the first time: the heuristic is Go-only, so a TypeScript monorepo gets exit 2 and --suggest-project-config refuses --project-language entirely. That reframes it from an evidence gap to a legibility gap. #278
  • The released binary in a real CI runner. Testing used a locally built macOS/arm64 binary. Linux/Windows, container startup cost, and the signed-release path are unverified. The second pass added three concrete findings: there is no linux/arm64 build in .goreleaser.yaml, no Dockerfile for the CLI, and git cat-file --batch -Z requires Git ≥ 2.42 with no minimum declared anywhere. Also note that #55, whose title reads like it covers this, verifies the source tree on one platform and never touches a produced artifact. #276
  • Two rules never fired in ~50 runs — structure.react_component_orchestration_density and coupling.tight_constructor_init — because no TSX/React repo was available — and a third, coupling.deep_relative_import, that the first pass did not name. All four were individually confirmed to fire end-to-end when given a matching fixture, so this is a corpus gap, not broken rules. Separately, source_sink_pack turned out to be validated and then discarded: the README tells users to set it and it changes nothing. #260 #253
  • No systematic precision census. Misses were found trivially; a true-positive / false-positive count across real repos was not attempted. That census is the actual gate the PRD names, and as far as the evidence shows it has not been done by anyone. It now has an issue that defines it concretely — repositories, sample size, adjudicator, and the precision threshold that would unblock the security claim — because an open-ended research ticket is how this gets deferred again. One prerequisite: 25% of findings currently carry empty evidence and are not adjudicable. #260
  • The noise judgment is inferred, not observed. The 84%-single-pattern and 75%-vendor numbers are hard measurements; “nobody will own this report” is an inference from them, not a watched user abandoning one. Folded into the census rather than asserted as a separate finding. #260

Path to yes · in order

The shortest credible route out of pilot

None of these is large. The ordering is a real dependency sequence — each step unlocks the claim beside it.

  1. Make the tool report what is actually there. Classify signals in added files as introduced and fix the summary counters; analyze the head side of renames; stop misclassifying dotless-module imports as stdlib; and stop printing a clean verdict over input that was never examined. Removes every false all-clear.

    Unlocks → any run can be trusted at all

    Issues #284 — dotless module #262 — added-file lifecycle #264 — renames dropped #267 — false all-clear verdict

  2. Make failures fail. Configuration errors follow the ruled contract — exit 2, stderr, no stdout report. Positional arguments stop swallowing the flags after them. JSON stops omitting empty collections. The TypeScript sidecar becomes deployable outside this repository.

    Unlocks → safe to put in a CI pipeline

    Issues #275 — config-failure exit contract #269 — JSON key stability #273 — positional args #280 — TS sidecar

  3. Fix report ergonomics. rule_id and severity in text output; revision and resolved base in the diff-mode header; drop source_scope when unknown; stamp a tool version into the report; document the terms a reader meets first.

    Unlocks → “expand to Go teams as an advisory PR check”

    Issues #279 — text output fields #263 — diff provenance #270 — tool version #63 — README terms

  4. Cut the noise. Exclude vendor/ and TypeScript tests from production scope, and let --scope and --build-target compose instead of one silently voiding the other. Roll density rules up per file. Rank by magnitude. Stop firing on declared out-parameters. Ship the suppression mechanism.

    Unlocks → someone runs it a second time

    Issues #277 — vendored code #281 — TS source scope #283 — scope/build-target composition #261 — density rollup #272 — ranking #259 — advisory severity #268 — out-parameter precision #48 — suppression

  5. Publish the thresholds, then run the precision census the PRD already names as the gate — true positives, false positives, and known misses across 5–10 real repos. Close the Go write-side TOCTOU blind spot, and actually execute the released archives on the platforms they ship to.

    Unlocks → the word “security” in front of a customer

    Issues #266 — publish thresholds #260 — precision census #205 — TOCTOU act set #276 — release verification

Steps 1–3 alone are enough to expand to a named segment with stated caveats. Step 4 is what makes the tool sticky. Step 5 is what makes the security claim honest.

Two decisions blocked planning and have both been ruled. Configuration errors are usage errors — exit 2, stderr, no stdout — which gives every future config knob one rule to inherit instead of negotiating its own. And --scope and --build-target are not mutually exclusive: one is a filter policy, the other is classifier evidence, and the fix is to make them compose rather than to add a validation error. Folding --build-target into --scope as an enum value was considered and rejected, because TypeScript's evidence is a root tsconfig.json and a polyglot repository would then be able to declare evidence for only one language at a time.
