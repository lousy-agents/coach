# Source ledger (c): ground truth for code-quality tools

Track (c) of the Coach evaluation design: how ground truth is built and scored for code-smell, static-analysis and architecture-conformance tools, so the seeded fixtures, their manifest and the #260 precision census rest on measured practice. Each row was read from the primary source on 25 Nov 2026. Quotes are verbatim and short; line breaks inside a quote are joined and nothing else is changed. Where a source did not report something (for example an inter-rater agreement statistic), the row says "not reported" and states how that was checked. Design documents cite these rows as `c.N`.

Reading method: the fetch tool returned the PDF papers as raw bytes, so each PDF was downloaded and converted to text with `pdftotext`, and every quote below was matched against that text. The OWASP pages are HTML and were read as text. Section c.9 lists what could not be read in full.

## c.1 Madeyski and Lewowski, "MLCQ: Industry-Relevant Code Smell Data Set" (EASE 2020)

- URLs: https://madeyski.e-informatyka.pl/download/MadeyskiLewowski20EASE.pdf (paper), https://zenodo.org/records/3666840 (data set, v1.1, 13 Feb 2020), DOI 10.1145/3383219.3383264
- Key findings:
  1. The unit of labelling is a class or a function, and the label is a severity, not a yes/no: "We gathered reviews of four code smells–two on the class level (Blob and Data Class) and two on the function level (Feature Envy and Long Method)–from a total of 26 developers with professional experience". Severity is "critical, major, minor, and none"; the sample count is "14739 reviews of 4770 code samples".
  2. Reviewers were not trained, on purpose: "We did not conduct any training related to code smell identification". Reviewers could change their own assessment later.
  3. Disagreement is handled by a second pass on the contested samples, not by a statistic. The last phase "selected to perform a crosscheck—only from samples already tagged with severity higher than 'none'", taking "Samples selected from crosscheck were those that had only 1 review or 2 reviews with different severities", with the rule that a "developer could not crosscheck his or her own review". The paper says "there was less agreement on" class-level samples than function-level ones. An agreement statistic is not reported: a search of the paper text finds no kappa, Fleiss or Krippendorff, and "agreement" appears only in that one sentence.
  4. The label base rate is skewed, and the authors say so: "over 77% show no smells (none severity)", and "our code smell data set in large part describes what is not a code smell, instead of what is one". The crosscheck covered only samples first tagged above none, so "it is possible that some samples which should have severity above none do not have it", which is a recall hole in the labels themselves.
  5. Each released record carries `id` (the review), `reviewer_id`, `smell`, `severity`, `review_timestamp`, `type` (class or function), `code_name` (a fully qualified name) and a `link` to view the sample. The reviewers' experience survey is published separately and linked by reviewer id; 20 of 26 reviewers completed it.
- Design implication for Coach: the manifest and the #260 adjudication file should store one row per judgement (rater id, date, verdict, rationale), never one merged verdict per finding, so agreement can be computed afterwards. Add a second-rater pass on every contested or single-rated finding and report an agreement statistic, which MLCQ did not. Record the unit (function or file) and a stable name for it, and publish the prevalence of "not a smell" next to every precision figure.

## c.2 Palomba et al., "Landfill: An Open Dataset of Code Smells with Public Evaluation" (MSR 2015)

- URLs: https://www.cs.wm.edu/~denys/pubs/MSR'15-LandFill-CRC.pdf (author copy), https://zenodo.org/records/6080422 (data set, v1.0, 1 May 2015), DOI 10.1109/MSR.2015.69
- Key findings:
  1. The motivation is the subjectivity of the oracle: "often people do not agree on the presence of a smell instance. Thus, even oracles built for the same software system and for the same set of smells are very likely to be different if built by different people."
  2. How the 243 instances of five smells in 20 open-source projects were made: "one of the authors manually identified instances of five considered smells ... This process took approximately four weeks of work. Then, another author validated the produced oracle". The second author rejected few: "Only six of the smells identified by the first author were classified as false positives by the second author", and after discussion "two of the six smells were classified as false positives (and thus removed from the oracle)".
  3. The authors state what the oracle cannot show: the second pass "does not ensure that the defined oracle is complete (i.e., it includes all affected components)", and "the oracles we produced ... may contain errors and omissions, mainly due to the subjectiveness of discriminating smelly" and non-smelly code.
  4. Each oracle is tied to a revision: the table reports "the git snapshot-id of the system version on which the oracle has been built".
  5. Public evaluation: users can add a missing instance, and "positive scores are useful to easily identify the smell instances for which there is a high agreement among the LANDFILL's users" while negative scores mark "likely wrong" instances; users "can also leave comments ... to explain the rationale behind a positive/negative evaluation". An agreement statistic is not reported (no kappa in the text).
- Design implication for Coach: pin every fixture and every census repository to a commit id, and store the oracle against that id. Cost the oracle in person-weeks before committing to a size: four weeks of one author's time bought 243 instances. Keep the rationale string with each verdict, keep rejected candidates in the file (marked rejected) rather than deleting them, and record that a manifest proves precision-style claims but not completeness unless the seeding itself lists every defect.

## c.3 Tempero et al., "The Qualitas Corpus: A Curated Collection of Java Code for Empirical Studies" (APSEC 2010)

- URL: https://cs.uwaterloo.ca/~m2nagapp/courses/CS846/1189/papers/tempero_apsec10.pdf (the paper's own DOI is not printed in the text read)
- Key findings:
  1. Why a fixed corpus: "none of these studies use the same set of systems, making it difficult to compare or combine results", and "because full details of the systems analysed are not provided, we are limited in our ability to replicate them".
  2. What a corpus must pin down beyond the project name: "it is frequently the case that what is distributed in the source version is not the same as what is in the binary version", and the source "often includes 'infrastructure' code, such as that used for testing", which "could bias the results of the study". Unreported choices make results "difficult to analyse (or even fully evaluate)".
  3. Design of the corpus: release 20100719 "has 100 systems, 23 systems with multiple versions, with 495 versions total". A version is named "<system>-<versionid>"; each version directory has a `metadata` directory with "detailed information about the contents of the version" and a `.properties` file.
  4. The corpus is reused as a smell benchmark: Fontana et al. (c.4) used release "20120401r", which "is composed of 111 systems", of which "The systems selected for the analysis are 74" because "the systems must be compilable to correctly compute the metrics values".
- Design implication for Coach: every corpus entry in the #260 census records the repository, the exact commit, the include and exclude rules (tests, vendored code, generated code) and the language set, so the same files are scanned on re-run. The `vendor/` problem in #260 (60 of 79 findings in one repository) is the same issue the paper names for test and infrastructure code. Record why a system was dropped, as Qualitas did for systems that would not compile.

## c.4 Arcelli Fontana et al., "Comparing and experimenting machine learning techniques for code smell detection" (Empirical Software Engineering, 2016), and its replication by Di Nucci et al., "Detecting Code Smells using Machine Learning Techniques: Are We There Yet?" (SANER 2018)

- URLs: https://mmantyla.github.io/Fontana_EMSE_2016_Comparing_and_Experimenting_Machine_Learning_Techiniques_for_Code_Smell_Detection.pdf (DOI 10.1007/s10664-015-9378-4), https://fpalomba.github.io/pdf/Conferencs/C24.pdf (DOI 10.1109/SANER.2018.8330266)
- Key findings:
  1. Labelling procedure, Fontana et al.: candidates were first flagged by detection rules ("Advisors") and sampled in strata of how many Advisors agreed, because "code smells density in code is low, so the composition of a randomly sampled training set will have a great chance to contain only a few instances affected by code smells". Then "The labeling evaluation was performed by three MSc students specifically trained for the task". They worked "with the only support of the Eclipse IDE. No metric values were supplied to the students ... and they did not know the number of Advisors giving a positive evaluation." Conflicts, meaning "no total agreement among all students", were settled "by discussion". The result is "1986 instances were manually labeled (826 positive and 1160 negative instances)". No agreement statistic is reported: the only "kappa" in the paper is a classifier metric.
  2. The authors name the label risk themselves: "The main threat to internal validity is the difficulty of deciding when a code smell candidate is actually a real code smell or not", and "A limitation in the manual labeling process is the use of students instead of professionals."
  3. The replication shows that dataset construction decided the headline result. Fontana et al. balanced each smell to "140 smelly instances and 280 non-smelly ones", and the replication finds that "the high performance achieved by Arcelli Fontana et al. can be attributed to the dataset exploited, rather than to the real capabilities of prediction models", with models "up to 90% less accurate in terms of F-Measure" on a less balanced set, where "non-smelly elements ... are 5/6 of the total instances (whereas in the datasets by Arcelli Fontana et al. they were 2/3 of the instances)". The replication traces this to the metric distributions of smelly and non-smelly elements being "very different", so the classes were "clearly distinguishable".
  4. The replication reused the original labels deliberately, "in order to rely on their classification of the dependent variable (i.e., the smelliness of source code elements), thus reducing the bias of a different manual classification", and still lists possible imprecision in the Qualitas Corpus metrics as a threat.
- Design implication for Coach: a precision or recall number from a fixture whose positives and negatives are easy to tell apart is not evidence about real code. Seeded fixtures need hard negatives (code that resembles a seeded shape but is correct) and a stated positive-to-negative ratio, and the report prints that ratio next to every score. Do not choose the census sample by Coach's own output, because the Advisor-strata design lets the detectors shape the oracle; #260's "random sample of 30" per rule is the safer rule, and the fixed manifest should say which sampling frame produced each number. Blind the adjudicator to the rule's confidence or severity, as these labelers were blind to the Advisors.

## c.5 OWASP Benchmark project (scoring and test-case definition)

- URLs: https://owasp.org/www-project-benchmark/ (current project page, latest release v1.2), https://owasp.org/projects/benchmark?tab=scoring (scoring tab), https://wiki.owasp.org/index.php/Benchmark (archived wiki, no longer maintained). Pages read as text.
- Key findings:
  1. Every case carries one label for one issue: "Each test case in Benchmark has a single intentional CWE that is either a True or False Positive. These are documented in the expectedresults-1.2.csv file." The wiki shows the file's shape: a `# test name category real vulnerability CWE` header, a `Benchmark version` comment, then rows such as `BenchmarkTest00001 crypto TRUE 327`.
  2. The score uses both error rates and ignores guessing: "False Positive Rate: FP / ( FP + TN )", the score is the "Normalized distance from the 'guess line' TPR - FPR", and "The Benchmark Accuracy Score is essentially a Youden Index". By the formula, a tool that flags every case scores zero.
  3. The false-positive half of the labels is argued, and the wiki records the rulings: cases where unsafe data "is replaced with static content" before the sink are scored as false positives, because the weakness cannot be exploited.
  4. The authors say what the suite is not: "the majority of them are considerably simpler than real applications".
  5. Results must be reproducible: "We won't recognize any results that aren't easily reproducible", which means the out-of-the-box installation and version numbers, any configuration or tailoring, any changes to default rules, and the steps to run the tool. The suite is versioned: "Version 1.0 of the Benchmark was published on April 15, 2015 and had 20,983 test cases", and the wiki table gives 21,041 cases for v1.1 and 2,740 for v1.2.
- Design implication for Coach: the manifest should be a flat, versioned table with one row per seeded site and a boolean "is a real defect" column, with true-negative decoys in the same file, so both a true-positive rate and a false-positive rate can be computed and combined into a score that a flag-everything tool cannot win. Carry a manifest version and a per-row rationale for contested decoys. Publish Coach's own configuration and version with every score, as OWASP requires of tool vendors. State plainly that fixtures are simpler than the real repositories in the #260 census.

## c.6 NIST SATE VI report (SP 500-341) and the Ockham report on Juliet 1.3 (IR 8304)

- URLs: https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.500-341.pdf (DOI 10.6028/NIST.SP.500-341, June 2023), https://nvlpubs.nist.gov/nistpubs/ir/2020/NIST.IR.8304.pdf (DOI 10.6028/NIST.IR.8304)
- Key findings:
  1. A hand-built manifest carries errors that only a comparison with tool output finds. IR 8304: "Examining the tool outputs led us to find several systematic mistakes in the Juliet 1.3 test suite and thousands of mistakes in its manifest of known errors." The authors had no independent list: "We did not have an independent list. Instead, we used the source code, which has hints in comments. The hints are inconsistent."
  2. Mismatches are triaged, not assumed to be tool errors: "Initial comparison between findings and the Juliet manifest almost always produced thousands of mismatches", and "An unmatched finding may indicate valid bugs missing from the manifest, findings that are incorrectly encoded, or findings that are not extracted at all." In one case, "We removed the 26 incorrect entries from the manifest" because the code "does not have a bug".
  3. Precision alone misleads on paired good and bad code. SATE VI defines a stricter metric: "Discrimination ... recognizes a true positive on a specific flawed test case only if a tool did not report a false positive on the corresponding fixed test case", and "A tool that flags all sites (good and bad) indiscriminately would achieve a discrimination rate of 0 %". It explains that precision "is relevant only when good sites dominate buggy sites", since with equal numbers "a tool could indiscriminately flag both good and bad sites as flawed and still achieve a precision of 50 %".
  4. Injected bugs are not the same as natural ones: "Regardless of the test case, injected bugs were not found by tools at the same rate as existing bugs, implying that their quality needs to improve." Tools found "bugs with lower complexity more readily than bugs with higher complexity", and the paper lists bug-injection quality criteria such as being "embedded in existing control and data flows".
- Design implication for Coach: pair every seeded defect with a fixed twin in the fixture and score discrimination (flagged the bad site and not its fixed twin) as well as recall and precision. Treat the manifest as a second artefact under test: validate it before use by running the oracle (reference) refactor against it and by reviewing every finding that matches no manifest row, and give those findings their own verdict in the #260 adjudication record, for example `manifest_gap`, beside `true_positive` and `false_positive`. Because injected defects are found at different rates from natural ones, keep the real-repository census (#260) alongside the seeded suite, and do not read the fixture recall as the recall on real code.

## c.7 Just et al., "Are Mutants a Valid Substitute for Real Faults in Software Testing?" (FSE 2014)

- URLs: https://homes.cs.washington.edu/~mernst/pubs/mutation-effectiveness-fse2014.pdf (the paper's DOI is not printed in the text read)
- Key findings:
  1. The problem it addresses is the one Coach's fixtures have: "Because the set of faults in a program is usually unknowable, this definition is not useful ... In place of real faults, testing research often uses mutants, which are artificial faults — each one a simple syntactic variation — that are systematically seeded throughout the program under test."
  2. The comparison is against real, verified faults: "357 developer-fixed and manually-verified real faults" in 5 programs, against 230,000 mutants.
  3. Seeding stands in for real defects only in part: "The results show the existence of a coupling effect for 73% of real faults", "10% of real faults require a new or stronger mutation operator", and "17% of real faults are not coupled to mutants". Mutant detection correlated with real-fault detection more strongly than statement coverage did.
  4. What seeding misses: "Most of the real faults not coupled to mutants were due to incorrect algorithms", and faults "caused by extra code that has to be deleted" are not coupled either.
  5. Their own threats: the 357 faults were found "by automatically linking bug identifiers from the bug tracking system to the version control revisions that resolved them", a link that "does not produce an unbiased sample of real faults", and all 5 programs "are well-tested", which may "limit the applicability of the results".
- Design implication for Coach: a seeded fixture is evidence about the shapes it seeds, not about all defects of that kind. Each manifest row records its seed method (derived from a real fix, mutated by an operator, or hand-written) and the seeding catalogue states which shapes it cannot express, as the paper does for algorithm-level faults. Recall is reported per seeded shape, never as one number for a rule. Also state how the real findings in the census were found, since the link-based sampling above is biased in a way the fixture is not.

## c.8 Maffort et al., "Heuristics for Discovering Architectural Violations" (WCRE 2013)

- URL: https://www.llp.dcc.ufmg.br/Publications/Art2013/2013_wcre_archlint.pdf (paper on ArchLint, an architecture-conformance tool; the DOI is not printed in the text read)
- Key findings:
  1. Two kinds of violation, scored separately: "divergences" (a present dependency the architecture forbids) and "absences" (an expected dependency that is missing). On one industrial system the tool "detected 119 violations ..., with a precision of 46.7% and a recall of 96.2%, for divergences", and on four open-source systems "For the systems with architectural violations, ArchLint achieved precision results ranging from 57.1% to 89.4% and recall ranging from 16.2% to 93.1%". The open-source systems were taken from "an independent study on reflexion models".
  2. The oracle is a named human: "We asked the architect to carefully examine the triggered violations and to classify them as true or false positives. Since the architect has a complete domain of SGA's architecture and implementation, he is the right expert to play an oracle role in our study."
  3. Recall for divergences was measurable because the dependency set is enumerable: "we asked the architect to inspect and classify all dependencies established between the classes in the last version considered", and the authors note this "was a not simple task, but at least it was manageable". Recall for absences was not measured: "it would require finding the whole set".
  4. Thresholds change precision a great deal: for absence violations, across the combinations of two thresholds tried, "the precision has varied from 15.4% to 57.1%", so a single reported number depends on the setting chosen.
  5. Their threat to validity: the architect "might be influenced to design a model favoring ArchLint", which they answer by noting "we never explained to the architect the heuristics followed by ArchLint".
- Design implication for Coach: for `architecture.layer_violation` and `architecture.layer_bypass` (out of the first #260 census, per its scope boundaries), the fixture manifest should list every cross-layer edge, allowed and forbidden, so recall is exact and not sampled. Keep forbidden-edge rows (divergences) apart from required-edge rows (absences), since Coach checks only the first. State that the person who wrote the layer model did not see the rule's implementation, and print the configuration the numbers came from, since precision moved with thresholds here.

## c.9 What was not read in full, and gaps

- Pruijt, Köppe, van der Werf and Brinkkemper, "The accuracy of dependency analysis in static architecture compliance checking" (Software: Practice and Experience, 2017, DOI 10.1002/spe.2421): only the abstract was read, because the full-text PDF returned HTTP 403. Abstract, verbatim: "Ten tools were tested and compared by means of a custom-made benchmark", whose Java code "contains 34 different types of dependencies", and "On the average, 77% of the dependencies in our custom-made test software were reported, while 72% of the dependencies within a module of FreeMind were reported." The abstract does not name the tools, so it is not known from it whether ArchUnit was tested. The scoring method, the list of hard-to-detect dependency types and the threats were not read. It is a lead to open with an institutional login, not a ledger row.
- Murphy, Notkin and Sullivan on reflexion models (FSE 1995 and TSE 2001) were not read; a search result only confirmed that the technique compares a high-level model with a source model. No source read here evaluates ArchUnit-style dependency rules against a ground truth.
- No source read here reports an inter-rater agreement statistic for a code-smell data set (MLCQ, Landfill and Fontana et al. do not; checked by searching each text for kappa, Fleiss, Krippendorff and Cohen). The agreement protocol for #260 therefore has no published precedent in these sources and has to be designed and justified by Coach.
- The Fontana and Di Nucci rows rest on text extracted from two-column PDFs; the Di Nucci quotes were reassembled from interleaved columns and checked against both columns.

## Cross-cutting implications for the manifest schema and #260's adjudication records

1. One row per judgement, not per finding (c.1, c.2, c.4): rater, date, verdict, rationale, and the revision the code was read at. Never overwrite; add a row.
2. A second rater on every contested or single-rated finding, with an agreement statistic computed and reported (c.1, c.4); no source here provides one to copy.
3. A verdict for the manifest's own errors (c.6): `manifest_gap` for a finding that matches no row and is correct, beside `true_positive`, `false_positive`, `unactionable_true_positive` and `not_adjudicable` already in #260.
4. Seeded defects come in pairs, a bad site and a fixed twin, scored by recall, false-positive rate and discrimination (c.5, c.6), with hard negatives and a stated positive-to-negative ratio (c.4).
5. Provenance per seeded row (c.7): real fix, operator mutation or hand-written; the seeding catalogue lists the shapes it cannot express, and recall is reported per shape.
6. Pin and describe the corpus (c.2, c.3): commit id, include and exclude rules, reasons for exclusion, tool version and configuration with every score (c.5).
7. For architecture rules (c.8): enumerate the full edge set so recall is exact, separate divergences from absences, and keep the model's author blind to the rule's implementation.
